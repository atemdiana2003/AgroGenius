# Security and privacy

- Passwords use Argon2id; access tokens are short-lived HS256 JWTs. Refresh and reset values are random, stored only as SHA-256 hashes, expiring; refresh rotates atomically and reset tokens are claimed once. Browser refresh tokens are returned only in the HttpOnly cookie. JSON transport requires explicit `X-Refresh-Transport: body` opt-in for non-browser clients.
- Require independent random 32+ character `JWT_ACCESS_SECRET` and `DEVICE_TOKEN_PEPPER`. Production requires `COOKIE_SECURE=true`, HTTPS, restricted CORS, a managed database, and secret-manager injection. Never commit `.env`, device secrets, database dumps or sensitive logs.
- Cookie-authenticated unsafe HTTP methods require an `Origin` exactly present in `ALLOWED_ORIGINS`; missing, `null`, or unapproved origins receive `403 CSRF_ORIGIN_REJECTED`. `SameSite=Lax` is an additional defense, not the CSRF policy. Bearer-token API calls without the refresh cookie are unaffected.
- Registration cannot choose ADMIN. Provision administrator and device credentials through a restricted operator process. Admin endpoints require role middleware. Farmers/buyers operate on owned data.
- Public listings return display name/community only, not phone/email. Contact is a buyer-initiated request, owner-approved and permitted only when that listing explicitly opted into phone contact. Password reset is unavailable in production until a real delivery provider exists; the endpoint returns the same `503 RESET_DELIVERY_UNAVAILABLE` for all identifiers. Local development tokens are never emitted in production.
- SMS requires phone, current opt-in, no opt-out and outside configured quiet hours. There is no production SMS integration; the simulated adapter does not send messages.
- Request logs redact credential-like properties and omit body data. Generic errors omit stack/SQL secrets. Review proxies and hosting logs for headers/cookies.
- Browser access token should be short-lived/in-memory. Refresh cookie is HttpOnly, SameSite=Lax, Secure in production, path-scoped. For cookie-authenticated mutations the API enforces exact Origin allow-list checks; test browser deployments and do not rely on `SameSite` alone.
- Proxy trust defaults to zero hops. Set `TRUST_PROXY_HOPS` only to the exact number of trusted reverse proxies; ensure the API cannot also be reached directly, because trusting a hop count on an exposed origin can let clients spoof forwarded IPs and evade rate limits.
- Optional payments use server-side Fapshi collection only for seller-confirmed offers with an explicit integer XAF total. Credentials and raw provider responses are never exposed or logged; `x-wh-secret` is compared in constant time and the status API is authoritative. Payment does not trigger sale/inventory mutations, escrow or payouts. Refunds are manual and no Fapshi sandbox/live transactions were performed locally.
- Minimize precise location; existing farm coordinates are optional and not required for a listing. CSV exports are admin-only, batch-oriented and exclude phone/email.
- Define retention/deletion, consent language, access controls and incident response with local stakeholders before field deployment; these are operational/legal decisions not established by this prototype.

Threat-oriented checks still required before production: exhaustive cross-user/admin-route coverage, refresh/reset race tests, login throttling behind the deployed trusted-proxy topology, secret rotation, backup access review, formal penetration/security review, and provider sandbox/callback validation.
