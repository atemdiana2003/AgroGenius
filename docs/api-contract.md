# REST API contract

All API routes are under `/api`; timestamps are RFC3339/ISO UTC strings; IDs are UUID strings. Decimal database quantities and prices may serialize as decimal strings; clients must not assume binary floating-point currency accuracy. List responses use `{ "data": [], "meta": { "page": 1, "pageSize": 25, "total": 0 } }`. Success objects use `{ "data": {}, "meta": {} }`. Errors are `{ "error": { "code": "...", "message": "...", "details": [], "requestId": "..." } }`. No production error contains stack/SQL details.

## Authentication and common conventions

Public routes: registration, login, reset request/confirmation, reference list, public active listings/prices, `/health`. Other `/api` routes use `Authorization: Bearer <accessToken>`. Refresh credentials use the HttpOnly, SameSite=Lax `hg_refresh` cookie by default; production requires Secure. Non-browser clients must explicitly send `X-Refresh-Transport: body` on login, refresh, and logout; only then is a refresh token returned in/accepted from JSON. Requests with cookies need HTTPS and deployment-reviewed CSRF/origin protections. Registration accepts only `FARMER`/`BUYER`; no public admin route exists.

Password reset is deliberately unavailable in production until a real delivery provider is configured. The request endpoint returns `503 RESET_DELIVERY_UNAVAILABLE` for every identifier in production, without looking up accounts. Local development may return a one-time token for testing; it is never returned in production.

`Idempotency-Key` (UUID recommended) or `clientOperationId` on selected create writes stores the committed JSON response by actor and operation ID. Replay returns the original response with `Idempotency-Replayed: true`; the first commit returns `false`. Never reuse a key for a different payload. Versioned PATCHes require `expectedVersion`; stale writes return `409 VERSION_CONFLICT` with safe current version. `409 TRANSACTION_CONFLICT` indicates caller may retry safely with the same key. Every list supports `page` (default 1), `pageSize` (default 25, max 100) where implemented.

When an idempotent business/constraint operation fails after processing begins, its business transaction rolls back and a separate sync record stores `FAILED` or `CONFLICT` plus a safe error code. Query `/sync/operations/:clientOperationId` to inspect it. Replaying a recorded failed/conflicted key returns `409 SYNC_PREVIOUSLY_FAILED` or `409 SYNC_PREVIOUS_CONFLICT`; correct/resolve the issue and use a new operation ID. Validation rejected before idempotent processing creates no sync record.

## Optional Fapshi payments

Payment endpoints are disabled unless `PAYMENTS_ENABLED=true`. `POST /payments/offers/:id` is BUYER-only and accepts no body fields; it requires an `Idempotency-Key` UUID. The offer must belong to the caller, be `ACCEPTED`, and already have `confirmedAt` set by the seller. The server derives the amount from `offeredPrice`, which this project explicitly interprets as the total agreed offer value. It must be an integer amount in `XAF` and at least 100. An unpriced, non-XAF, fractional-XAF or unconfirmed offer returns a safe `409`. The client cannot choose an amount, phone, provider transaction ID, currency, or final status.

The successful response uses the standard `{data,meta}` wrapper and returns the internal payment UUID, opaque reference, offer ID, amount/currency, provider/mode, hosted checkout URL and local lifecycle status. It excludes provider credentials, authorization headers, raw provider data and provider transaction IDs. A first pending initiation returns `201`; an exact replay of a committed request returns `200` with the same payment; `INITIATION_UNKNOWN` returns `202` and must not be retried using a new key until reconciled. Reusing a key for a different payer/offer/payload returns `409 IDEMPOTENCY_KEY_REUSED`; pending/successful/uncertain payment already associated with the offer returns `409 PAYMENT_ALREADY_INITIATED`.

`GET /payments/:id` is restricted to the owning buyer and refreshes the provider status only when the last check is at least 11 seconds old. Provider errors are surfaced with safe codes; unmatched or mismatched provider reference, amount, user, or transaction ID never advances state. Fapshi `SUCCESSFUL`, `FAILED`, and `EXPIRED` webhooks are accepted at `POST /payments/fapshi/webhook` only with a configured `x-wh-secret`; the API queries the documented Fapshi status endpoint and checks internal linkage before persisting a transition. The webhook payload or checkout redirect alone is never proof of payment. Payment does not alter inventory, sale confirmation, escrow, or payouts. See [Fapshi payment setup and limits](./payments-fapshi.md).

Configure `PAYMENT_PROVIDER=mock` for a non-production deterministic pending-only simulation (`provider: MOCK`, `mode: simulated`, no checkout URL) or `PAYMENT_PROVIDER=fapshi` with `FAPSHI_MODE=sandbox` and service credentials to call Fapshi. Production payment collection requires `PAYMENT_PROVIDER=fapshi`, live mode and secret-manager credentials. API hosts are fixed by mode; no caller-supplied provider URL exists. Configuration names are in `.env.example`.

## Status codes and error codes

`200` read/update, `201` create, `400` invalid input or bad JSON, `401` missing/expired/invalid auth, `403` role/consent/origin failure, `404` missing or not owned, `409` stale version/duplicate/inventory/status/idempotency conflict, `429` throttling, `500` generic internal failure. Common codes include `VALIDATION_ERROR`, `INVALID_JSON`, `UNAUTHORIZED`, `FORBIDDEN`, `NOT_FOUND`, `VERSION_CONFLICT`, `TRANSACTION_CONFLICT`, `DUPLICATE_RESOURCE`, `INVENTORY_CONFLICT`, `LISTING_UNAVAILABLE`, and `RATE_LIMITED`. Error messages/details are safe for UI display.

Shared Zod schemas are the source for common request names and field validation; see `packages/contracts/src/index.ts`. The current API is a pilot, not yet a frozen compatibility promise. Introduce `/api/v1` before breaking changes.
